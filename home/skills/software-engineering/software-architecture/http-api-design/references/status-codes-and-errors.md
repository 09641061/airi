# Step 4 — Status codes and RFC 7807 / RFC 9457 Problem Details

HTTP response status codes communicate operational results at the protocol level. Infrastructure, reverse proxies, API gateways, service meshes, and client HTTP libraries rely exclusively on the status line to manage routing, retries, metrics, and circuit breakers.

## Status Code Taxonomy

### 2xx — Success
* **`200 OK`**: Standard response for successful `GET`, `PATCH`, or `PUT` returning a body.
* **`201 Created`**: Resource created successfully via `POST` or `PUT`. **Must** include a `Location` header specifying the URI of the new resource (`Location: /v1/orders/ord-9921`).
* **`202 Accepted`**: Request accepted for asynchronous processing; background task initiated but not yet completed.
* **`204 No Content`**: Action succeeded, response body is intentionally empty (standard for `DELETE`, or `PUT`/`PATCH` when no return payload is requested).

### 3xx — Redirection & Caching
* **`301 Moved Permanently` / `308 Permanent Redirect`**: Resource has permanently relocated to a new URI.
* **`304 Not Modified`**: Result of a conditional read (`If-None-Match` or `If-Modified-Since`). Indicates client's cached representation is fresh. Response body must be empty.

### 4xx — Client Errors
* **`400 Bad Request`**: Malformed request syntax, invalid JSON, or unrecognized query parameters.
* **`401 Unauthorized`**: Authentication is missing, expired, or invalid. **Must** include `WWW-Authenticate` header.
* **`403 Forbidden`**: Client is authenticated but lacks required authorization/permissions to access the resource.
* **`404 Not Found`**: Target resource URI does not exist.
* **`405 Method Not Allowed`**: HTTP method unsupported for target URI. **Must** include `Allow` header (`Allow: GET, POST`).
* **`409 Conflict`**: Mutation conflicts with current resource state (e.g. unique-key violation, illegal state transition).
* **`412 Precondition Failed`**: Conditional validation failed (e.g. `If-Match` header value does not match current server `ETag`).
* **`415 Unsupported Media Type`**: Sent `Content-Type` is unsupported.
* **`422 Unprocessable Content`**: Request is syntactically valid JSON, but fails domain/semantic validation rules.
* **`429 Too Many Requests`**: Rate limit exceeded. Include `Retry-After: <seconds>` header.

### 5xx — Server Errors
* **`500 Internal Server Error`**: Unexpected, unhandled server exception. Never expose internal stack traces or database schema details in production payloads.
* **`502 Bad Gateway`**: Upstream service or dependency returned an invalid response.
* **`503 Service Unavailable`**: Service temporarily overloaded or under maintenance; pair with `Retry-After`.
* **`504 Gateway Timeout`**: Upstream proxy/service failed to respond within configured SLA timeout.

## Key Distinctions
* **401 vs 403**: *Identity* (`401`: "Who are you? Authenticate") vs *Permission* (`403`: "I know who you are, but you cannot perform this operation").
* **400 vs 422**: *Syntactic Syntax Error* (`400`: unparseable JSON, illegal types) vs *Semantic Invariant Violation* (`422`: well-formed JSON, but requested withdrawal exceeds available balance).

## RFC 7807 / RFC 9457: Problem Details Schema

To eliminate proprietary, fragmented error formats across microservices, all error responses must adopt the `application/problem+json` media type.

```json
{
  "type": "https://api.example.com/errors/insufficient-funds",
  "title": "Insufficient Funds",
  "status": 422,
  "detail": "Account ACC-8891 has an available balance of 120.00 USD, which is less than the requested transfer of 500.00 USD.",
  "instance": "/v1/accounts/ACC-8891/transfers/tx-994812",
  "invalid-params": [
    {
      "name": "amount",
      "reason": "Amount exceeds the account's available credit limit."
    }
  ]
}
```

### Problem Details Attributes:
* **`type` (URI, Required)**: A stable, resolvable URI identifying the error classification. Clients branch programmatically on `type`, never on `title` or human-readable strings.
* **`title` (String, Required)**: Short, human-readable summary of the problem type (remains constant for all occurrences of the error type).
* **`status` (Integer, Required)**: The HTTP status code generated by the origin server (must match the HTTP response status line).
* **`detail` (String, Optional)**: Human-readable explanation specific to this particular occurrence of the problem.
* **`instance` (URI, Optional)**: URI reference identifying the specific occurrence or target resource of the failure.
* **`invalid-params` (Array, Optional)**: Structured array detailing specific field-level validation errors.
